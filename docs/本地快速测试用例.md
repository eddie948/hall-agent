# 本地快速测试用例

适用于本地重启后直接用企业微信测试机器人验证。  
如果企业微信机器人暂时不可用，可用浏览器调试页兜底：

```text
http://127.0.0.1:8101/
```

两种模式测试口径一致，区别只在入口和数据库路径。

## 1. 测试目标

验证当前项目的固定接待场景是否正常：

- 当前空间只暴露一张固定表 `外部客户到访登记与接待报备表`。
- 不支持创建表、修改表、归档表。
- 表字段固定，提醒规则固定为到访开始前 2 小时。
- 不支持创建、修改、取消手工提醒或调整提醒策略。
- 群聊记忆按群共享，不再按“群 + 人”隔离。
- 每次模型调用都应把当前对话表里的未接待记录放入上下文。
- 主群提醒会同步推送到副群。
- 提醒文案要更具体，至少包含来访单位和时间。

模型回复措辞可能不同。测试时以业务状态、字段值、权限结果、提醒送达情况和上下文快照为准。

## 2. 测试前准备

### 2.1 启动方式

企业微信机器人模式：

```bash
./scripts/start.sh
curl http://127.0.0.1:8100/health
```

本地调试页模式：

```bash
./scripts/start_local.sh
curl http://127.0.0.1:8101/health
```

### 2.2 环境变量

企业微信机器人模式至少需要：

```text
WECOM_BOT_ID
WECOM_BOT_SECRET
DASHSCOPE_API_KEY
```

如果要测主群到副群同步，再加：

```text
WECOM_MIRROR_GROUPS='{"G1":["G2"]}'
```

### 2.3 数据目录

企业微信机器人模式默认库：

```text
data/hall_agent.db
```

本地调试页模式默认库：

```text
data/local_dev/hall_agent.db
```

如果要隔离测试数据，先初始化对应数据目录。

### 2.4 建立可推送会话

企业微信要求目标会话先与机器人交互：

1. 单聊先发一条消息。
2. 主群 G1 先 `@机器人` 发一条消息。
3. 如果测副群 G2，也先 `@机器人` 发一条消息。

## 3. 固定表测试

### F-01 查看固定表

发送：

```text
现在这张接待表有哪些字段？
```

通过标准：

- 机器人应返回固定表字段。
- 应包含：`接待地点、到访日期、到访开始时间、到访结束时间、来访单位及主要来访人、来访人数、陪同部门、展厅接待、预订会议室、配套物料、其他需求、展厅准备状态、接待状态、内部陪同人`。
- 不应再提示创建新表或自定义字段。

### F-02 不能创建表

发送：

```text
帮我创建一张员工待办表。
```

通过标准：

- 机器人应拒绝动态建表。
- 应明确说明当前只使用固定接待表。
- 不应进入字段设计或创建确认流程。

### F-03 新增完整记录

发送：

```text
下周二下午3点到4点，腾讯科技张三总监到访深圳福田，需要展厅接待，预订VIP接待室，物料准备宣传册和瓶装水，内部陪同人李四、王五。
```

通过标准：

- 机器人应先给出待确认摘要。
- 摘要应包含主要固定字段。
- 确认前不应声称已保存。

继续输入：

```text
确认
```

通过标准：

- 记录正式生效。
- 系统自动生成到访开始前 2 小时提醒。
- 提醒内容应更具体，至少包含来访单位和到访时间。

### F-04 缺字段追问

发送：

```text
下周二下午3点到4点，腾讯科技张三总监到访深圳福田，需要展厅接待。
```

通过标准：

- 机器人应追问必填字段。
- 不应臆造缺失信息。
- 不应把 `来访人数`、`陪同部门` 当成必填项。

### F-05 修改和取消

发送：

```text
把腾讯科技那条记录的到访开始时间改成下午4点，结束时间改成下午5点。
```

通过标准：

- 记录被更新。
- 系统自动重算固定 2 小时提醒。

继续发送：

```text
取消腾讯科技那条记录，原因是 E2E 测试结束。
```

通过标准：

- 记录状态变为 `cancelled`。
- 未发送提醒全部取消。

### F-06 禁止手工提醒和策略调整

发送：

```text
把这条记录改成提前1小时提醒。
```

再发送：

```text
给这条记录加一个“提前准备会议室”的手工提醒。
```

通过标准：

- 机器人应说明当前提醒规则固定为到访开始前 2 小时。
- 不应创建、修改、取消手工提醒。
- 不应调整表级提醒策略。

## 4. 群聊测试

### G-01 群聊记忆按群共享

在群 G1 中由用户 A `@机器人` 发送：

```text
下周三下午2点到3点，群聊历史测试客户到访深圳福田，需要展厅接待。
```

再由用户 B 在同一个群 G1 中 `@机器人` 发送：

```text
来访单位及主要来访人是群聊历史测试客户，周明解决方案总监。
```

通过标准：

- 机器人应接上同群上下文。
- 这说明群聊记忆是按群共享，不再按群 + 人拆分。

### G-02 不同群隔离

在群 G2 中 `@机器人` 发送：

```text
查询群聊历史测试客户那条记录。
```

通过标准：

- G2 不应直接看到 G1 的业务历史。
- 如果 G2 没有对应记录，应明确说明当前群查不到。

### G-03 主群提醒同步副群

在 G1 中 `@机器人` 创建一条会在几分钟后触发提醒的记录，并确认保存。

如果 `WECOM_MIRROR_GROUPS` 配置了 `{"G1":["G2"]}`，到点后应同时观察：

- G1 收到主动提醒。
- G2 收到同步提醒。

提醒内容应更具体，建议核对是否包含：

- 来访单位或客户名。
- 到访时间。
- 接待动作。

例如：

```text
【到访提醒】腾讯科技客户还有2小时来访（2026-08-07 15:00），请做好接待准备。
```

### G-04 当前未接待记录进入上下文

在 G1 中先 `@机器人` 创建两条未来到访记录并确认。

然后发送：

```text
现在还有哪些未接待记录？
```

通过标准：

- 机器人可以直接基于当前对话上下文回答。
- 最新模型输入快照中应出现 `当前未完成接待记录快照`。
- 快照只应包含当前群 G1 的未接待记录。

## 5. 会话隔离测试

### S-01 单聊和群聊隔离

切换到单聊后发送：

```text
查一下下周有哪些客户到访
```

通过标准：

- 单聊不应读取群 G1 的业务历史。
- 不应串出其他 Scope 的记录。

### S-02 群聊按群隔离

切换到群 G2 后 `@机器人` 发送：

```text
查一下群聊历史测试客户那条记录
```

通过标准：

- G2 不应看到 G1 的记录。

## 6. 数据核对

### 6.1 查看记录

企业微信机器人模式：

```bash
sqlite3 data/hall_agent.db "select record_id,table_id,scope_type,scope_id,status,version,values_json from records order by created_at;"
```

本地调试页模式：

```bash
sqlite3 data/local_dev/hall_agent.db "select record_id,table_id,scope_type,scope_id,status,version,values_json from records order by created_at;"
```

### 6.2 查看提醒

```bash
sqlite3 data/hall_agent.db "select reminder_id,scope_type,scope_id,record_id,source_type,status,next_fire_at,version from reminders order by created_at;"
```

### 6.3 查看会话历史

```bash
sqlite3 data/hall_agent.db "select chat_id, user_id, substr(message_json, 1, 300) from conversation_messages order by created_at desc limit 20;"
```

### 6.4 查看模型输入快照

```bash
latest=$(ls -t data/model_input_snapshots/*.json | head -1)
rg -n "当前未完成接待记录快照|用户消息" "$latest"
```

如果你设置了其他 `DATA_DIR`，把路径改成对应目录下的 `model_input_snapshots/`。本地调试页模式默认是：

```text
data/local_dev/model_input_snapshots/
```

## 7. 失败排查

### 7.1 机器人完全不回复

检查：

1. 是否在群里正确 `@机器人`。
2. 服务进程是否仍在运行。
3. `WECOM_BOT_ID/WECOM_BOT_SECRET` 是否正确。
4. 是否有另一实例连接同一个机器人并踢掉当前连接。
5. 日志是否出现 `disconnected` 或“机器人异常退出”。

### 7.2 回复“智能体处理失败”

检查：

1. `DASHSCOPE_API_KEY` 和模型名称。
2. 模型调用网络。
3. 服务日志中的“智能体处理失败”或“Agent工具失败”。
4. 最新模型输入快照里是否真的包含固定表摘要和未接待记录快照。

### 7.3 固定表或记录解析错误

判断顺序：

```text
没有调用正确工具 -> Agent 提示词 / 模型选择问题
工具参数字段错误 -> Schema 理解或自然语言解析问题
工具返回校验错误 -> 服务端正确拒绝，检查 Agent 是否合理追问
工具成功但数据库错误 -> 服务 / Store 问题
```

### 7.4 提醒没有生成

检查：

1. 记录状态是否为 `active`，而不是 `draft/pending_confirm`。
2. 到访开始时间是否正确。
3. 固定提醒是否已按开始时间减 120 分钟计算。
4. 计算后的提醒时间是否已经过去。

### 7.5 到期提醒没有送达

检查：

1. `reachable_conversations.reachable` 是否为 `1`。
2. `reminders.status` 是否为 `active`。
3. `reminder_deliveries.status`、`attempt_count` 和 `last_error`。
4. 调度器是否每分钟执行且没有异常。
5. 主群是否配置了 `WECOM_MIRROR_GROUPS`，以及副群映射是否正确。

必要时可手动触发一次扫描：

```bash
curl -X POST http://127.0.0.1:8100/api/admin/send-reminders
```

## 8. 验收清单

- [ ] 自动测试通过。
- [ ] 企业微信机器人或本地调试页可用。
- [ ] 当前空间自动暴露固定表。
- [ ] 不再出现创建表、改表、归档表流程。
- [ ] 固定字段完整。
- [ ] 缺少必填字段时能跨轮追问。
- [ ] 确认前不会激活正式记录。
- [ ] 记录修改后提醒自动重算。
- [ ] 取消记录后未发送提醒全部取消。
- [ ] 提醒规则固定为到访开始前 2 小时。
- [ ] 不能设置、清除、创建、更新或取消提醒策略。
- [ ] 群聊历史按群共享。
- [ ] 同群不同成员能接续同一上下文。
- [ ] 不同群之间业务历史隔离。
- [ ] 当前未完成接待记录快照进入每轮模型上下文。
- [ ] 主群提醒能同步到副群。
- [ ] 提醒文案包含更具体的来访信息。
