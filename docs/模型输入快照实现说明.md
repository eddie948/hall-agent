# 模型输入快照实现说明

## 需求目标

每次实际调用模型时，在 `data/model_input_snapshots/` 下单独保存一份完整输入。
快照应满足：

- 覆盖每一次模型 HTTP 请求，而不只是每次 Agent run。
- 包含模型实际收到的完整请求数据，包括 system prompt、历史消息、工具定义、
  工具调用与返回、模型名称和模型参数。
- 文件经过格式化，可直接人工阅读。
- 快照功能不依赖 Logfire 是否启用。

## 原实现的问题

原实现通过 Logfire 的可选 `before_model_request` hook 写快照，存在三个问题：

1. 只有启用并成功配置 Logfire 时才可能执行。未启用 Logfire、当前 Logfire 版本
   不提供该 hook，或初始化失败时，都不会保存文件。
2. 快照内容由 `prompt`、历史消息和手工收集的工具 schema 重新拼装，不是最终发送
   给模型供应商的请求，可能遗漏框架生成的 system message、最终工具结构或模型参数。
3. 外围 Agent run 与实际模型调用不是一一对应。一次 run 在执行工具后可能再次调用
   模型，因此只在 run 外围记录无法准确做到“一次模型调用一个文件”。

## 修改思路

最可靠的捕获位置是模型供应商 HTTP 客户端的请求 hook。此时 Pydantic AI 和 OpenAI
兼容适配器已经完成所有输入组装，HTTP body 就是即将发送给 DashScope
`chat/completions` 的完整请求。

处理流程如下：

```text
Agent 组装消息和工具
  -> OpenAIChatModel 转换为 DashScope 兼容请求
  -> HTTPX request hook 捕获最终 JSON body
  -> 格式化并写入独立文件
  -> 发送同一个 HTTP request 给 DashScope
```

这种设计保证捕获范围与实际模型请求一致。工具循环产生的第二次、第三次请求会分别
经过 HTTP hook，因此分别生成快照。

## 易读格式与一致性边界

HTTP hook 首先读取实际请求 body，然后用标准 JSON 解析器解析，并以 UTF-8、两空格
缩进、中文不转义的形式写入文件。

格式化后的文件与网络请求在 JSON 数据层面完全一致：

- 字段和值一致。
- 数组内容和顺序一致。
- 嵌套结构一致。
- 不增加用于调试的外围字段。

文件字节不会与网络 body 逐字节一致，因为缩进、换行以及等价的字符串转义形式会变化。
这是“易读格式”的必然结果，不影响从快照还原模型看到的结构化输入。

## 具体修改

### `src/agent/model_input_snapshot.py`

- 使用 HTTPX request hook 捕获 `/chat/completions` 的 POST 请求。
- 使用 `json.loads` 校验并解析实际请求体。
- 使用 `json.dumps(..., ensure_ascii=False, indent=2)` 输出易读 JSON。
- 使用配置项 `scheduler_timezone` 指定的时区生成本地时间戳；默认是
  `Asia/Shanghai`，不依赖服务器操作系统时区。
- 使用时间戳、`chat_id`、`message_id` 和随机后缀生成唯一文件名；文件名主体中的
  非字母数字字符统一替换为下划线。
- 使用 `ContextVar` 关联并发 Agent run 与各自的文件名信息，避免会话串写。

### `src/agent/llm_client.py`

- 新增带快照 hook 的 HTTPX 客户端。
- 新增 `SnapshotAlibabaProvider`，把该客户端交给 DashScope 的 OpenAI 兼容模型。
- 在 `run_agent_loop` 中设置本次调用的 `chat_id` 和 `message_id` 上下文。
- 使用 `async with agent` 管理 HTTP 客户端生命周期，确保请求结束后释放连接。

### `src/observability.py`

- 删除依赖 Logfire `before_model_request` 的旧快照实现。
- Logfire 继续负责 traces 和通用可观测性，但不再决定本地快照是否生成。

### 其他文件

- `.gitignore` 忽略 `data/model_input_snapshots/`，避免包含业务上下文的文件被提交。
- `docs/PydanticAI架构优化设计.md` 更新快照行为说明。
- `src/tests/test_record_store.py` 增加格式化、HTTP hook 和 transport 级测试。

## 文件行为

文件名示例：

```text
2026_07_16_10_30_15_123456_chat123_msg456_a1b2c3d4.json
```

前七段分别表示年、月、日、时、分、秒和微秒。默认时区为 `Asia/Shanghai`。
例如 `chat/room:01` 会写成 `chat_room_01`，避免斜杠、冒号等特殊字符影响文件路径。

文件内容示例：

```json
{
  "model": "qwen3-max",
  "messages": [
    {
      "role": "system",
      "content": "..."
    },
    {
      "role": "user",
      "content": "..."
    }
  ],
  "tools": []
}
```

若一次 Agent run 触发三次模型请求，该目录会产生三个文件。HTTP 请求重试也属于一次
实际发送尝试，因此会再次经过 hook 并生成新的快照。

## 失败策略

快照在 HTTP 请求真正发送前同步完成。如果目录创建、JSON 解析或文件写入失败，异常会
阻止该模型请求继续发送。这样可以避免“模型已经收到输入，但本地没有对应快照”的情况。

## 验证

测试覆盖以下行为：

- 文件名包含当前 `chat_id` 和 `message_id`。
- 保存文件是带缩进且中文可直接阅读的合法 JSON。
- 保存内容解析后与实际 HTTP body 完全相等。
- MockTransport 实际收到的 body 是原请求，证明格式化快照不会修改待发送请求。
- 非 `chat/completions` 请求不会被误记录。
