# 动态记录与提醒系统设计

## 1. 目标

项目提供两套模型能力：

```text
RecordManagementCapability
  -> 动态记录表和记录管理

ReminderManagementCapability
  -> 手工提醒和表级自动提醒管理
```

每个企业微信单聊用户或群聊是一个独立数据空间。用户可以用自然语言定义记录格式，后续消息按照该格式解析、校验和保存。SQLite 是唯一业务数据源。

系统不再包含固定接待字段、企业微信智能表格、云端同步 outbox 或云表初始化流程。

## 2. 核心原则

- 模型只表达业务意图并调用静态业务工具。
- Scope、操作者和消息 ID 只能来自可信企业微信回调。
- 动态格式保存为结构化 Schema，不保存为可执行提示词。
- 模型负责从自然语言提取候选字段值，服务端负责最终验证。
- 查询条件是结构化数据，模型不能生成 SQL。
- 记录和提醒的联动由服务层固定执行。
- 提醒只能发送消息，不能定时执行任意代码或业务命令。
- 所有资源读取和写入都进行 Scope 校验。

## 3. 身份与权限

### 3.1 Actor 和 Scope

`Actor` 是实际发起操作的成员：

```text
actor_user_id = from.userid
```

`Scope` 是资源所属空间：

```text
单聊：scope_type=user,  scope_id=from.userid
群聊：scope_type=group, scope_id=chatid
```

当前仅在公司内部单企业使用，不引入 `tenant_id`。

运行时上下文：

```text
actor_user_id
scope_type
scope_id
chat_type
message_id
```

以上字段不出现在模型工具参数中。

### 3.2 权限规则

所有资源访问首先验证：

```text
resource.scope_type == context.scope_type
resource.scope_id == context.scope_id
```

Scope 不匹配时统一返回 `RESOURCE_NOT_FOUND`，不泄露资源是否存在。

| 操作 | 个人 Scope | 群 Scope |
| --- | --- | --- |
| 创建/查看记录表 | 本人 | 当前群成员 |
| 修改/归档表格式 | 本人 | 表创建者 |
| 配置表级自动提醒 | 本人 | 表创建者 |
| 记录增删改查 | 本人 | 当前群成员 |
| 手工提醒增删改查 | 本人 | 当前群成员 |

机器人 API 不提供群管理员身份，因此第一版以表创建者作为群表配置管理员。

## 4. 动态记录表 Schema

### 4.1 受控结构

业务格式是开放的：用户可以定义任意表名、字段名称、字段数量、必填规则和枚举选项。

Schema 能力是受控的：只允许系统支持的字段类型和校验属性，不允许脚本、SQL、公式执行或任意嵌套对象。这样服务端才能稳定验证、查询和计算提醒时间。

支持的字段类型：

```text
text
integer
number
boolean
date
time
datetime
enum
user
location
url
```

字段属性：

```text
key             稳定的小写英文键，创建后不可修改
name            用户可见名称
type
required
default_value
description
aliases
enum_options
minimum
maximum
semantic_role
status          active | deprecated
```

### 4.2 公司访问表示例

以下只是动态表样例，不是系统内置固定格式：

```json
{
  "name": "公司访问日程",
  "creation_policy": "confirm",
  "fields": [
    {
      "key": "title",
      "name": "标题",
      "type": "text",
      "required": true,
      "semantic_role": "schedule_title"
    },
    {
      "key": "start_at",
      "name": "开始时间",
      "type": "datetime",
      "required": true,
      "semantic_role": "schedule_start_at"
    },
    {
      "key": "visitor_company",
      "name": "来访单位",
      "type": "text",
      "required": true,
      "aliases": ["客户", "公司"]
    },
    {
      "key": "visitor_count",
      "name": "人数",
      "type": "integer",
      "minimum": 1
    }
  ],
  "time_config": {
    "timezone": "Asia/Shanghai",
    "start": {
      "datetime_field": "start_at"
    }
  }
}
```

同一套能力也可以创建设备维护、合同到期、内部会议等完全不同的表。

### 4.3 时间锚点

相对提醒不能根据字段名猜测时间。记录表必须显式配置：

```text
schedule_start
schedule_end
```

每个锚点可以引用：

- 一个 `datetime` 字段；或者
- 一个 `date` 字段加一个 `time` 字段。

没有时间锚点的表仍可管理记录，但不能配置关联记录的相对提醒。

### 4.4 Schema 版本

- 表从 `schema_version=1` 开始。
- 每次格式修改递增版本并保存不可变快照。
- 更新工具必须传 `expected_schema_version`。
- 字段 `key` 和 `type` 创建后不可修改。
- 删除字段采用 `deprecated`，不清除历史记录值。
- 记录再次修改时按当前 Schema 重新校验。

## 5. RecordManagementCapability

### 5.1 表定义接口

```text
create_record_table
list_record_tables
get_record_table
update_record_table
archive_record_table
```

`create_record_table` 输入：

```text
name
description
creation_policy = immediate | confirm
fields[]
time_config（可选）
```

`update_record_table` 使用操作列表，避免整份 Schema 覆盖时误删字段：

```text
rename_table
update_description
update_creation_policy
add_field
update_field
deprecate_field
reorder_field
update_time_config
```

### 5.2 记录接口

```text
create_record
confirm_record
list_records
get_record
update_record
cancel_record
```

创建流程：

```text
定位记录表
  -> 读取完整 Schema
  -> 模型解析 values
  -> 服务端规范化和验证
  -> 缺少必填字段：保存当前 Actor 的草稿并返回 missing_fields
  -> confirm 策略：pending_confirm
  -> immediate 策略：active
```

同一 Actor 在同一张表中最多有一个 `draft/pending_confirm`，避免多轮补充串到其他成员的记录。

记录状态：

```text
draft
pending_confirm
active
cancelled
```

`list_records` 支持：

```text
filters: eq, ne, gt, gte, lt, lte, contains, in
sort: asc, desc
limit
cursor
```

服务端验证字段和操作符，当前实现读取当前 Scope/表的候选记录后在应用层执行类型安全过滤，不接受 SQL 文本。

`update_record` 和 `cancel_record` 使用 `expected_version` 做乐观并发控制。

## 6. ReminderManagementCapability

### 6.1 手工提醒接口

```text
create_reminder
list_reminders
get_reminder
update_reminder
cancel_reminder
```

独立提醒：

```json
{
  "content": "提交周报",
  "trigger": {
    "type": "absolute",
    "at": "2026-07-17T17:00:00+08:00"
  }
}
```

记录关联提醒：

```json
{
  "record_id": "REC_xxx",
  "content": "客户即将到访",
  "trigger": {
    "type": "relative_to_record",
    "anchor": "schedule_start",
    "offset_minutes": -120
  }
}
```

### 6.2 表级自动提醒接口

```text
get_table_reminder_policy
set_table_reminder_policy
clear_table_reminder_policy
```

每张表最多有一套自动提醒策略，策略可以包含多条规则。

例如所有记录在前一天 18:00 和开始前 1 小时提醒：

```json
{
  "table_id": "TBL_xxx",
  "rules": [
    {
      "type": "day_before",
      "anchor": "schedule_start",
      "days_before": 1,
      "at_time": "18:00"
    },
    {
      "type": "relative_to_record",
      "anchor": "schedule_start",
      "offset_minutes": -60
    }
  ],
  "apply_to": "new_records"
}
```

`apply_to`：

```text
new_records         只影响以后激活的记录
all_active_records  立即为现有 active 记录生成或更新提醒
```

规则类型：

```text
day_before
relative_to_record
```

“前一天 18:00”属于 `day_before`。“从创建日起每天 18:00 提醒直到日程开始”属于周期提醒，第一版不支持。

### 6.3 策略与具体提醒

表级策略是模板，不是发送任务。记录激活时，服务根据规则生成具体提醒：

```text
source_type=table_policy
source_rule_id=稳定规则 ID
```

用户手工创建的提醒：

```text
source_type=manual
```

因此修改或清除表策略只影响策略生成的提醒，不影响手工提醒。

固定联动：

```text
记录确认/立即生效
  -> 根据表策略生成提醒

记录时间修改
  -> 重算表策略提醒
  -> 重算手工相对提醒

记录取消
  -> 取消全部未发送关联提醒

清除表策略
  -> 取消该策略生成的未发送提醒
  -> 保留手工提醒
```

这些联动在服务层事务内执行，不要求模型再次调用提醒工具。

## 7. 统一工具结果

成功：

```json
{
  "success": true,
  "operation": "create_record",
  "data": {},
  "message": "记录已创建"
}
```

失败：

```json
{
  "success": false,
  "operation": "create_record",
  "error_code": "VALIDATION_FAILED",
  "message": "记录字段校验失败",
  "field_errors": [],
  "missing_fields": []
}
```

主要错误码：

```text
RESOURCE_NOT_FOUND
PERMISSION_DENIED
VALIDATION_FAILED
SCHEMA_VERSION_CONFLICT
RECORD_VERSION_CONFLICT
REMINDER_POLICY_VERSION_CONFLICT
REMINDER_VERSION_CONFLICT
INVALID_FILTER
INVALID_TIME_ANCHOR
REMINDER_TIME_IN_PAST
REMINDER_ALREADY_SENT
```

## 8. 本地数据库

业务表：

```text
record_tables              当前表定义和 schema_json
record_table_versions      Schema 历史快照
records                    动态 values_json 和记录版本
table_reminder_policies    每张表的自动提醒规则
reminders                  手工或策略生成的提醒定义
reminder_deliveries        发送实例、租约、重试和幂等键
reachable_conversations    可主动推送的个人/群会话
audit_events               表、记录、策略和提醒审计
message_results            消息幂等结果
conversation_messages      Pydantic AI 多轮历史
```

所有时间规范化后保存。提醒的 `next_fire_at` 和投递时间使用 UTC ISO 8601，表时间锚点按 `time_config.timezone` 解释。

SQLite 连接启用外键约束。动态字段查询第一阶段在应用层完成；数据规模需要时再引入 JSON 投影索引。

## 9. 提醒投递

目标映射：

```text
scope_type=user  -> chatid=userid, chat_type=1
scope_type=group -> chatid=chatid, chat_type=2
```

企业微信要求目标会话此前与机器人交互。收到可信消息时更新 `reachable_conversations`。

调度器每分钟执行：

```text
原子 claim 到期 delivery
  -> 设置 processing 和两分钟租约
  -> 企业微信主动推送
  -> 成功：delivery=sent, reminder=sent
  -> 失败：1、5、15 分钟退避重试
  -> 超过次数：delivery/reminder=failed
```

`idempotency_key` 和租约防止多实例重复发送。

## 10. 代码结构

```text
src/
  domain/
    context.py              ActorContext 和 Scope
    table_schema.py         Schema、字段验证和时间锚点

  agent/
    capabilities.py         两套模型 Capability
    schemas.py              静态工具参数模型
    prompts.py              模型行为规则
    llm_client.py           Pydantic AI 和运行依赖
    brain.py                消息幂等、历史和 Agent 入口

  services/
    authorization.py        Scope 和表管理权限
    table_service.py        表定义和 Schema 版本
    record_service.py       动态记录 CRUD
    reminder_service.py     手工提醒、表策略和记录联动

  records/
    store.py                SQLite Schema、事务和持久化

  scheduler/
    jobs.py                 提醒 claim、发送和重试

  bot/
    wecom_bot.py            企业微信长连接和主动推送
```

依赖方向：

```text
bot -> agent -> capabilities -> services -> store -> SQLite
scheduler -> store -> bot sender
```

模型工具不能直接操作 Store。

## 11. Agent 工作流

创建表：

```text
用户描述格式
  -> 模型生成受控 Schema 摘要
  -> 用户确认
  -> create_record_table
```

添加记录：

```text
list_record_tables
  -> 无法唯一定位则让用户选择
get_record_table
  -> 按 Schema 提取 values
create_record
  -> 缺字段继续追问
  -> pending_confirm 时展示摘要
confirm_record
```

查询/修改：

```text
定位表并读取 Schema
  -> list_records
  -> 多条候选时让用户选择
  -> get/update/cancel
```

模型不得猜测动态字段 key、表或记录，不得在工具成功前声称操作完成。

## 12. 测试与验收

必须覆盖：

- 个人和群 Scope 隔离。
- 群成员可操作记录但不能修改他人创建的表格式。
- 动态类型、必填、枚举和数值约束。
- Schema 和记录乐观锁冲突。
- 多轮草稿只属于当前 Actor。
- 表策略为新记录和现有活动记录生成提醒。
- `day_before` 和相对分钟提醒计算。
- 修改记录时间后提醒重算。
- 取消记录后提醒取消。
- 清除策略不影响手工提醒。
- 投递 claim、租约、重试和幂等。
- 企业微信个人和群发送类型正确。

第一阶段完成标准：用户可以在个人或群空间创建任意受控格式的表，稳定管理记录和提醒；本地 SQLite 是唯一数据源，代码和文档中不存在固定接待或云表同步业务链。
