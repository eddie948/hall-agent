# 企业微信端到端测试指南

## 1. 测试目标

本文用于在企业微信中验证展厅保障接待 Agent 的完整业务链：

```text
企业微信消息
  -> 长连接机器人
  -> Pydantic AI Agent
  -> 固定表 / 固定提醒工具
  -> SQLite
  -> 后台调度器
  -> 企业微信主动推送
```

重点验证：

- 当前空间只暴露一张固定表 `外部客户到访登记与接待报备表`。
- 不再支持创建表、修改表、归档表。
- 表字段固定，提醒规则固定为到访开始前 2 小时。
- 不再支持设置、清除、创建、修改、取消提醒策略或手工提醒。
- 群聊记忆按群隔离，不再按“群 + 人”隔离。
- 每次模型调用都应把当前对话表里的未接待记录放入上下文。
- 主群提醒会同步推送到副群，且提醒文案要更具体。

模型回复措辞可能不同。测试时以业务状态、字段值、权限结果、提醒送达情况和上下文快照为准，不要求逐字匹配本文示例。

## 2. 测试资源

建议准备：

| 资源 | 用途 | 是否必需 |
| --- | --- | --- |
| 测试用户 A | 单聊测试、主群创建者 | 是 |
| 测试用户 B | 验证群聊共享记忆 | 推荐 |
| 测试群 G1 | 主群业务测试 | 是 |
| 测试群 G2 | 副群 / 镜像群提醒测试 | 推荐 |
| 单聊机器人 | 验证个人空间 | 是 |
| 后端终端 | 查看服务日志 | 是 |
| SQLite CLI | 辅助核对数据库 | 推荐 |

测试前缀建议使用当前日期，例如：

```text
E2E_20260807
```

重复执行时请改成新的后缀，例如 `E2E_20260807_02`。

## 3. 测试前准备

### 3.1 确认配置

`.env` 至少配置：

```text
WECOM_BOT_ID
WECOM_BOT_SECRET
DASHSCOPE_API_KEY
SCHEDULER_TIMEZONE=Asia/Shanghai
```

如果要测主群到副群的同步推送，再加：

```text
WECOM_MIRROR_GROUPS='{"G1":["G2"]}'
```

确认没有其他进程正在使用同一个机器人长连接。一个机器人同一时间只能保持一个有效长连接，新连接会踢掉旧连接。

### 3.2 运行自动测试

```bash
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 pytest -q
```

通过标准：全部通过。

### 3.3 使用隔离数据库

推荐端到端测试使用单独数据目录：

```bash
mkdir -p data/e2e
DATA_DIR=./data/e2e python -m src.admin.init_db
```

后续所有启动和数据库检查命令都应继续携带：

```text
DATA_DIR=./data/e2e
```

如果决定直接使用默认数据库，先备份：

```bash
cp data/hall_agent.db /tmp/hall_agent_before_e2e.db
```

### 3.4 启动服务

```bash
DATA_DIR=./data/e2e \
LOG_DIR=./data/e2e/logs \
MODEL_INPUT_SNAPSHOT_DIR=./data/e2e/model_input_snapshots \
./scripts/start.sh
```

预期日志包含：

```text
Application startup complete
Scheduler started
```

不应出现：

```text
WECOM_BOT_ID/WECOM_BOT_SECRET 未配置
wecom-aibot-python-sdk 未安装
机器人异常退出
```

检查进程、日志和健康状态：

```bash
./scripts/status.sh
tail -f "data/e2e/logs/app_$(date +%F).log"
curl http://127.0.0.1:8100/health
```

预期：

```json
{"ok":true,"version":"v0.2"}
```

### 3.5 建立主动推送资格

企业微信要求目标会话此前与机器人交互：

1. 用户 A 在单聊中给机器人发送 `E2E 测试开始`。
2. 用户 A 在群 G1 中 `@机器人` 发送 `E2E 群测试开始`。
3. 如测试副群 G2，也在群 G2 中发送一次消息。

这些消息会把对应个人或群记录为可主动推送。

## 4. 记录测试结果

每完成一个用例，记录：

| 字段 | 内容 |
| --- | --- |
| 用例编号 | 例如 `F-01` |
| 执行时间 | 企业微信消息时间 |
| 操作用户 / 群 | 用户 A、群 G1 等 |
| 实际回复 | 机器人最终回复 |
| 是否通过 | 通过 / 失败 |
| 日志或截图 | 失败时必填 |
| 备注 | 与预期的差异 |

失败时保留原始消息，不要马上换一种说法重试。先记录第一次失败，方便区分是解析问题还是业务工具问题。

## 5. 固定表测试

以下步骤由用户 A 在机器人单聊中执行。

### F-01 不能创建新表

发送：

```text
帮我创建一张员工待办表。
```

通过标准：

- 机器人应拒绝动态建表诉求。
- 机器人应说明当前空间只使用固定的 `外部客户到访登记与接待报备表`。
- 不应进入表结构设计、字段确认、创建成功等流程。

### F-02 查看固定 Schema

发送：

```text
现在这张接待表有哪些字段？
```

通过标准：

- 结果中应包含这些固定字段：
  `接待地点、到访日期、到访开始时间、到访结束时间、来访单位及主要来访人、来访人数、陪同部门、展厅接待、预订会议室、配套物料、其他需求、展厅准备状态、接待状态、内部陪同人`。
- 不应再出现“让我创建新表”或“自定义字段”的引导。

### F-03 新增完整到访记录

发送：

```text
下周二下午3点到4点，腾讯科技张三总监到访深圳福田，需要展厅接待，预订VIP接待室，物料准备宣传册和瓶装水，内部陪同人李四、王五。
```

通过标准：

- 机器人读取固定表 Schema。
- 如果信息足够，先返回待确认的记录摘要。
- 摘要应包含：接待地点、到访日期、开始/结束时间、来访单位及主要来访人、展厅接待、会议室、配套物料、内部陪同人等固定字段。
- 记录不会在未确认前声称已经正式保存。

继续输入：

```text
确认
```

通过标准：

- 记录被确认保存。
- 系统自动生成到访开始前 2 小时提醒。
- 提醒内容应更具体，至少包含来访单位和到访时间，而不是空泛的“有提醒了”。

### F-04 缺字段追问

发送：

```text
下周二下午3点到4点，腾讯科技张三总监到访深圳福田，需要展厅接待。
```

通过标准：

- 机器人应追问固定表中的必填字段。
- 不应臆造缺失值。
- 不应把 `来访人数`、`陪同部门` 这类可选字段当成必填。

### F-05 查询和修改记录

发送：

```text
查询腾讯科技那条有效记录。
```

通过标准：能定位到对应记录。

继续发送：

```text
把刚才那条记录的到访开始时间改成下午4点，结束时间改成下午5点。
```

通过标准：

- 记录被更新。
- 系统自动重算该记录的固定 2 小时提醒。
- 不需要也不应该再配置提醒策略。

### F-06 取消记录

发送：

```text
取消腾讯科技那条记录，原因是 E2E 测试结束。
```

通过标准：

- 记录状态变为 `cancelled`。
- 该记录所有未发送提醒均被取消。
- 查询有效记录时不再返回该记录。

### F-07 关闭提醒配置

发送：

```text
把这条记录的提醒改成提前1小时。
```

通过标准：

- 机器人应说明当前提醒规则固定为到访开始前 2 小时。
- 不应创建、修改、取消手工提醒。
- 不应调整表级提醒策略。

再发送：

```text
给这条记录加一个“提前准备会议室”的手工提醒。
```

通过标准同上。

## 6. 群聊测试

以下步骤由用户 A 或用户 B 在群 G1 中 `@机器人` 执行。

### G-01 群聊记忆按群隔离

用户 A 在群 G1 中发送：

```text
下周三下午2点到3点，群聊历史测试客户到访深圳福田，需要展厅接待。
```

通过标准：

- 机器人应继续当前群内上下文。
- 这条消息会进入 G1 的共享历史。

用户 B 接着在同一个群 G1 中发送：

```text
来访单位及主要来访人是群聊历史测试客户，周明解决方案总监。
```

通过标准：

- 机器人应接上 A 刚才发起的同群上下文。
- 这说明群聊记忆是按群共享，不是按“群 + 人”拆分。

再由任意群成员发送：

```text
确认
```

通过标准：记录被确认保存，且后续同群任意成员都能继续查询和修改。

### G-02 跨群隔离

用户 A 在群 G2 中 `@机器人` 发送：

```text
查询群聊历史测试客户那条记录。
```

通过标准：

- 群 G2 不应直接看到 G1 的业务历史。
- 如果 G2 没有对应记录，应明确说明当前群查不到，而不是串出 G1 的内容。

### G-03 主群提醒同步到副群

在 G1 中创建一条会在几分钟后触发提醒的记录，例如把开始时间设成当前时间后 2 小时 3 分钟，再确认保存。

预期：

1. 到点后，G1 收到主动提醒。
2. 如果 `WECOM_MIRROR_GROUPS` 配置了 `{"G1":["G2"]}`，G2 也收到同样的同步提醒。
3. 两边提醒内容应一致，并且比旧版本更具体。

提醒内容建议核对这些信息：

- 来访单位或客户名。
- 到访时间。
- 接待动作，例如“请做好接待准备”。

例如：

```text
【到访提醒】腾讯科技客户还有2小时来访（2026-08-07 15:00），请做好接待准备。
```

### G-04 当前未接待记录进入模型上下文

在 G1 中先创建两条未来到访记录并确认。

然后再发一条普通查询，例如：

```text
现在还有哪些未接待记录？
```

通过标准：

- 机器人可以直接基于当前对话上下文回答。
- 最新模型输入快照里应出现 `当前未完成接待记录快照`。
- 快照只应包含当前群 G1 的未接待记录，不应混入 G2 或其他会话的数据。

检查快照时可用：

```bash
latest=$(ls -t data/e2e/model_input_snapshots/*.json | head -1)
rg -n "当前未完成接待记录快照|用户消息" "$latest"
```

## 7. 数据库辅助核对

以下命令不代替企业微信测试，只用于失败定位。

### 7.1 查看固定表

```bash
sqlite3 data/e2e/hall_agent.db "select table_id,scope_type,scope_id,name,status,schema_version from record_tables order by created_at;"
```

### 7.2 查看记录

```bash
sqlite3 data/e2e/hall_agent.db "select record_id,table_id,scope_type,scope_id,status,version,values_json from records order by created_at;"
```

### 7.3 查看提醒

```bash
sqlite3 data/e2e/hall_agent.db "select reminder_id,scope_type,scope_id,record_id,source_type,status,next_fire_at,version from reminders order by created_at;"
```

### 7.4 查看会话历史


```bash
sqlite3 data/e2e/hall_agent.db "select scope_type,scope_id,reachable,last_interacted_at,last_delivery_error from reachable_conversations;"
```

## 8. 失败排查

### 8.1 机器人完全不回复

检查：

1. 是否在群里正确 `@机器人`。
2. 服务进程是否仍在运行。
3. `WECOM_BOT_ID/WECOM_BOT_SECRET` 是否正确。
4. 是否有另一实例连接同一个机器人并踢掉当前连接。
5. 日志是否出现 `disconnected` 或“机器人异常退出”。

### 8.2 回复“智能体处理失败”

检查：

1. `DASHSCOPE_API_KEY` 和模型名称。
2. 模型调用网络。
3. 服务日志中的“智能体处理失败”或“Agent工具失败”。
4. `MODEL_INPUT_SNAPSHOT_DIR` 下的模型请求快照。

### 8.3 固定表或记录解析错误

记录：

- 用户原始消息。
- 机器人回复。
- 对应模型输入快照。
- 工具日志中的工具名和参数。
- `record_tables.schema_json` 和 `records.values_json`。

判断顺序：

```text
没有调用正确工具 -> Agent 提示词 / 模型选择问题
工具参数字段错误 -> Schema 理解或自然语言解析问题
工具返回校验错误 -> 服务端正确拒绝，检查 Agent 是否合理追问
工具成功但数据库错误 -> 服务 / Store 问题
```

### 8.4 提醒没有生成

检查：

1. 记录状态是否为 `active`，而不是 `draft/pending_confirm`。
2. 到访开始时间是否已正确写入。
3. 固定提醒是否已按开始时间减 120 分钟计算。
4. 计算后的提醒时间是否已经过去。

### 8.5 到期提醒没有送达

检查：

1. `reachable_conversations.reachable` 是否为 `1`。
2. `reminders.status` 是否为 `active`。
3. `reminder_deliveries.status`、`attempt_count` 和 `last_error`。
4. 调度器是否每分钟执行且没有异常。
5. 主动发送目标是否正确：个人 `chat_type=1`，群 `chat_type=2`。
6. 主群是否配置了 `WECOM_MIRROR_GROUPS`，以及副群映射是否正确。

必要时可手动触发一次扫描：

```bash
curl -X POST http://127.0.0.1:8100/api/admin/send-reminders
```

如果配置了 `ADMIN_INIT_TOKEN`：

```bash
curl -X POST -H "X-Admin-Token: 实际令牌" http://127.0.0.1:8100/api/admin/send-reminders
```

手动扫描只发送已经到期的提醒，不会提前发送未来提醒。

## 9. 验收清单

### 必须通过

- [ ] 自动测试全部通过。
- [ ] 服务健康检查正常。
- [ ] 当前空间自动暴露固定表，不再出现创建表流程。
- [ ] 固定字段齐全，旧的动态表字段引导不再出现。
- [ ] 缺少必填字段时能跨轮追问并补全。
- [ ] 确认前不会激活正式记录。
- [ ] 记录修改后提醒自动重算。
- [ ] 取消记录后未发送提醒全部取消。
- [ ] 提醒规则固定为到访开始前 2 小时。
- [ ] 不能设置、清除、创建、更新或取消提醒策略。
- [ ] 群聊历史按群共享，不再按群 + 人拆分。
- [ ] 同群不同成员能接续同一上下文。
- [ ] 不同群之间业务历史隔离。
- [ ] 当前未完成接待记录快照进入每轮模型上下文。
- [ ] 快照只包含当前对话 / 当前群的数据。
- [ ] 主群提醒能同步到副群。
- [ ] 提醒文案包含更具体的来访信息。

### 可接受偏差

- 模型回复措辞与本文不同，但业务状态一致。
- 时间以 UTC 显示，但换算后与北京时间预期一致。
- 提醒因一分钟扫描周期在目标时间后延迟不超过约一分钟。

### 不可接受

- 跨个人或跨群读取到其他 Scope 的资源。
- 未确认就激活正式记录。
- 固定提醒生成重复有效提醒。
- 修改到访时间后仍按旧时间发送提醒。
- 主群提醒没有同步到配置的副群。
- 同一投递重复发送。

## 10. 缺陷记录模板

```text
标题：
用例编号：
测试时间：
用户 / 群：
测试数据前缀：E2E_20260807

前置状态：
用户原始消息：
机器人实际回复：
预期结果：
实际数据库状态：
服务日志：
模型输入快照文件：
企业微信截图：
是否可稳定复现：
补充说明：
```

完成测试后保留隔离数据库和日志，直到所有失败项分析结束。使用 `./scripts/stop.sh` 停止服务；确认数据不再需要时，再清理 `data/e2e/`。
